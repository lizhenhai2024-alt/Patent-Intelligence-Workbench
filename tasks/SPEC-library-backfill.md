# 规格：覆盖率检查与确认后补库（市场对标 v2 · A0b）

## 目标

本地库数据不全会直接影响智能体和情报分析的结论（2026-09-23 实测：本地 692 件、仅 6 个专利族已解析；抽查 15 件 KYB 公开件全部缺申请日/公开日）。本规格让软件：

1. 在分析前**量化**本地库对某个问题的覆盖程度；
2. 覆盖不足时**提议补库**，由用户确认后由程序（不是模型）联网检索、入库、补全；
3. 在补全后的本地库上分析，结论照旧只引用本地公开号，并记录本次补了什么。

原则不变：智能体回答过程中不联网；联网只发生在用户确认的补库步骤里；每件补入的专利都有来源记录。

## 决定（2026-09-23，产品负责人确认）

- 采用"先补库、再分析"，不采用"回答时直接联网"。
- 单次补库默认上限 **200 件**（可在设置中调整，硬上限 1000），原因是 EPO OPS 免费账号有流量限额（以 EPO 官方公布为准）。
- 排在开发顺序第 3 步：全文索引之后、分类号映射之前。

## 依赖

- 全文索引（`tasks/SPEC-fulltext-index.md`）：补入的 PDF 要进入全文索引，覆盖率中的本地命中数也用全文检索计算。
- 现有能力复用：`app/services/search_service.py`（检索与数据源回退）、`app/services/family_resolver.py`（专利族）、`app/downloads/`（PDF 下载与归档命名）、`app/library/service.py` 的 `ingest_search_response` / `ingest_family` / `ingest_download_summary`、`app/library/enrichment.py`（著录补全）。不新增数据源，不新增依赖。

## 覆盖率检查

- 输入：一组已确认的检索式（关键词、公司、技术节点、国家/局、日期范围）。
- 外部数：用同一检索式向已配置的数据源查询命中总数（`SearchPage.total_result_count`，EPO OPS 优先，Google Patents 回退），只取总数和第一页，不下载。数据源不返回总数时显示"外部总数未知"，不估算。
- 本地数：同一检索式在本地库（全文索引 + 著录字段）中的命中数。
- 输出：`外部约 N 件 / 本地 M 件 / 覆盖约 M/N`，按专利族与公开件分别列出；注明数据源、查询时间、检索式。覆盖率只是命中数之比，不代表"重要专利"的覆盖程度，页面上写明这一点。
- 日期完整度：本地命中中缺申请日/公开日的件数单独列出（直接影响按年份的分析）。

## 补库流程

1. 覆盖率低于阈值（默认 50%）或日期缺失率高于阈值（默认 20%）时，智能体结果顶部和情报分析页显示"建议补库"，附拟用检索式和预计件数。
2. 用户在确认框中可修改检索式、国家/局、日期范围和本次上限；点确认后才开始。
3. 程序按顺序执行（后台、有进度、可取消）：检索 → 按公开号去重（已在本地的跳过）→ 入库著录信息 → 解析专利族 → 下载 PDF（按现有归档命名规则放入所选 LocalLibrary 根目录）→ 补全日期等著录字段 → 更新全文索引。
4. 达到上限即停止，并说明"还有约 K 件未补"。
5. 结束后显示补库报告：新增公开件/专利族数、下载成功/失败数、仍缺日期的件数、各步骤的数据源。

## 来源与可追溯

- 每件补入的公开件在 `library_provenance` 中记录一条 `source_type = BACKFILL`，`source_ref` 为补库任务编号；任务本身（检索式、时间、数据源、上限、结果统计）保存为 JSON，放在应用数据目录的 `backfill_runs/` 下。
- 智能体和报告中注明"本次分析前于 <时间> 补充了 N 件（任务 <编号>）"。
- 公司归属沿用现有规则：精确实体解析；未知申请人进 `待归类`，不猜测。

## 边界

- 始终：联网补库必须由用户点确认；每次补库有上限；来源可追溯；失败不破坏本地数据（逐件事务，失败记录原因后继续）。
- 始终：补库由程序执行；智能体只提出建议和检索式，不直接调用联网工具。
- 需要时再问：定时自动补库（可在专利监控里做）；新增数据源（如智慧芽 API，属 M5）；提高硬上限。
- 绝不：回答过程中联网；从公开号或文件名推断日期后写入数据库；把外部检索结果当作本地证据引用（未入库的公开号不能作为回执）。

## 测试策略

- 覆盖率：假数据源返回总数 N、本地命中 M，输出比例正确；数据源不返回总数时显示"未知"。
- 补库：假数据源 + 假下载器，验证去重、上限、取消、逐件失败不中断、来源记录和任务 JSON。
- 智能体：覆盖率低时结果顶部出现"建议补库"；未入库的公开号引用仍被证据校验标红。
- 离线测试不需要网络和凭据。

## 验收标准

1. 在真实本地库上对"复原弹簧"或"KYB CDC 阀"做覆盖率检查，能显示外部数、本地数和日期缺失数。
2. 确认补库后，新增专利带来源记录、日期和全文索引；重新运行同一个问题，结论引用的公开号增多，且"局限与待确认"中的覆盖说明随之更新。
3. 新测试全部通过；`python scripts/ai_self_audit.py --full` 和 `git diff --check` 保持通过。

## 阶段 0：已知专利全文补全（2026-09-23 追加，先做）

在上面的"覆盖率检查 + 搜索发现新专利"之前，先做一个范围更小、价值更直接的版本：**只针对本地库里已经存在、但全文缺失或不完整的公开号**（`library_text_source.status` 为 `needs_ocr` / `partial` / `failed`，或完全没有记录），不做检索发现，直接用公开号向 EPO OPS 要官方权利要求书/说明书全文。真实库现状（2026-09-23 全文索引建成后）：完整 540、部分 11、需要 OCR 122，另有 19 件无 PDF——阶段 0 覆盖这 152 件。

- 数据源：`app.providers.epo_ops.EpoOpsProvider.get_fulltext_section(publication, "claims"|"description")`，已有实现，返回解析好的纯文本，不需要 OCR、不需要下载 PDF。
- 写入：复用 `app/library/fulltext.py` 的 `replace_text()`，`source_type="EPO_OPS"`，`source_ref="EPO_OPS:<公开号>"`，`pdf_sha256=None`。权利要求/说明书分段复用现有的 `_claim_segments`/`_description_segments`（EPO OPS 文本没有页码，`page_start`/`page_end` 记为空)。
- 来源记录：每件补入的公开号在 `library_provenance` 写一条 `source_type="BACKFILL"`，`source_ref=<任务ID>`；任务本身（时间、候选数、结果统计）写 JSON 到应用数据目录 `backfill_runs/`。
- 用户确认：桌面页面显示候选数量和默认上限（200，可调，硬上限 1000），用户点确认后才开始；后台执行、有进度、可取消；请求之间加小延时，避免触发 EPO OPS 限流；单件失败不中断整体任务，记录原因后继续。
- 不做：不搜索发现新专利号；不下载/拼接 PDF（后续如需要 PDF 本身，再做基于 `get_image_page_pdf` 的独立功能）；不覆盖已经是 `ok`/`partial` 且并非缺失的记录，除非其全文为空。
- 前置条件：需要已配置的 EPO OPS 凭据（`app.runtime.current_epo_credentials()`），未配置时提示去设置里填，不静默跳过。

后面的"覆盖率检查 + 搜索发现新专利"（原 SPEC 正文）保持不变，作为下一阶段。
